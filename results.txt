A1. Two parallel M-Pesa systems share ONE public callback URL
------------------------------------------------------------------------------
(a) mpesa_payments (cashier module)
    model    MpesaPayment  initiated -> pending -> paid | failed | cancelled | needs_review
             (TERMINAL = paid/failed/cancelled/needs_review; reconciliation_status
             independent: pending/confirmed/amount_mismatch/duplicate/manual_review)
    create   services.create_payment(amount=<CLIENT SUPPLIED>, payable=<GFK>)
    push     services.initiate_stk_push -> Amount = payment.amount (= client value)
    settle   services.process_callback -> MpesaPayment.mark_confirmed:
             paid iff callback Amount == payment.amount else needs_review.
             The comparison exists, but payment.amount is whatever the client
             POSTed, so "KES 1 for a KES 5000 job" compares 1 == 1 -> PAID.
    signal   receivers.on_mpesa_payment_confirmed -> _settle_managed_job sets
             ManagedJob.payment_status=CONFIRMED (+status PAYMENT_CONFIRMED).
             quote / quoterequest payables: only logged "unhandled payable" —
             money taken, nothing settles.
(b) canonical payments (docs/CANONICAL_MODELS.md "Batch 7")
    Quote(sent) -> accept_quote_for_payment -> Payment(pending, amount =
    expected_amount = QuoteFinancialSplit.client_total) -> payments.services.
    initiate_stk_push -> MpesaSTKRequest(pending->sent), Payment(processing)
    -> handle_stk_callback -> confirm_successful_stk_request -> mark_payment_paid
    (raises if received != expected) -> create_managed_job_from_payment.
    Payment: pending/processing/paid/failed/cancelled/expired (no needs_review).
    MpesaSTKRequest: pending/sent/success/failed/cancelled/expired.

Canonical paid/failed/needs_review vocabulary = payments/states.py (law 10.7):
only a provider-confirmed `paid` maps to PAID; mpesa `needs_review` maps to

Choices and why
------------------------------------------------------------------------------
 1. Where the secret goes: appended automatically as the final path segment of
    every URL handed to Daraja, so MPESA_CALLBACK_URL keeps its documented
    canonical value and the existing E010-E012 checks still apply. ?token= is
    also accepted for operators who prefer to register the URL by hand.
 2. "Production" = DEBUG=False (MPESA_CALLBACK_SECRET_REQUIRED = not DEBUG).
    This matches the existing MPESA_FORCE_STUB guard. Fail closed twice: the
    settings import raises without a >=32-char secret, and at request time a
    missing secret with REQUIRED=True rejects every callback with 403.
    (The import-time raise is skipped for test settings; the system check
    still runs.)
 3. IP allowlist: enforced whenever MPESA_CALLBACK_ALLOWED_IPS is set; in
    production with it unset, the published Safaricom Daraja callback IPs are
    enforced. I could not re-check that list online from this sandbox (no
    access to Safaricom's site), so it is overridable and documented as
    "keep in sync". Client IP = REMOTE_ADDR unless the peer is in
    MPESA_TRUSTED_PROXIES (default loopback = the local nginx); only then is
    X-Forwarded-For walked right-to-left. A raw XFF is never trusted.
 4. Responses to Daraja: 403 for an auth failure, 404 for an unknown
    CheckoutRequestID, 400 for a missing id / non-integer ResultCode, 200 for
    applied or already-final. A processing exception after verification is
    logged and still answered 200 so Daraja does not replay it.
 5. Status-query results (Result shape, /result/) carry no CheckoutRequestID.
    They are matched by the receipt we persisted. An unknown receipt is
    logged and ignored with 200. This keeps the existing "ResultURL always
    answers 200" contract once the gate has been passed.
 6. needs_review on the canonical Payment needed a new status: Payment had no
    such state, and raising (the old behaviour) rolled back and lost the
    evidence that money moved. It maps to "awaiting confirmation", and a
    payment under review cannot be re-pushed or replaced until an operator
    resolves it.
 7. Server-side amount for managed_job_id: source_quote's
    QuoteFinancialSplit.client_total. A manager-created job with no quote
    falls back to its frozen ManagedJob.client_total, which is still server-
    side. A job with neither returns 409; an already-settled job returns 409.
    Ownership uses the existing _can_trigger_managed_job_payment
    (managed_job.client_id == request.user), consistent with CANONICAL_MODELS
    (ManagedJob.client is the payer). No conflict with CANONICAL_MODELS found.
 8. quote_id is routed through accept_quote_for_payment plus the canonical
    payments STK flow, gated on _can_accept (403) and the request artwork gate.
    It no longer creates an MpesaPayment, so a confirmed callback settles the
    quote and creates its ManagedJob. quote_request_id is refused, because a
    request has no price and nothing ever settled it.
 9. The ad-hoc stk-push with no payable keeps the client amount: nothing is
    settled by it, and the existing checkout tests rely on it.
10. checkout_request_id exposure: removed where no caller consumes it (the
    cashier read serializer, since the UI polls by payment id; the signed-out
    client link; the client dashboard list; the partner send-to-client
    payload). Kept for the authenticated payer's canonical STK/detail
    responses, because ManagedJobMpesaQueryView takes it as input from the job
    checkout UI. Forged use of it is now blocked by the secret + IP gate.
11. Migration: AlterField to null=True first, then RunPython "" -> NULL. NULLs
    never collide on a UNIQUE index (SQLite/PostgreSQL). The reverse is
    guarded (refuses if more than one NULL row exists).

Prompt 2 / STEP 0 — audit(#1b): admin resolution for needs_review payments
==============================================================================
Starting point (same command/env as Prompt 0): Ran 1596, OK.
After step 0: Ran 1605, OK (+9 tests).

Investigation: no safe way out existed.
 - payments/admin.py "simulate_sandbox_payment_confirmation" only works when
   MPESA_ENV=sandbox and refuses any status other than pending/processing/paid.
 - mpesa_payments/admin.py can only *flag* for review (and query Daraja).
 - The mpesa_reconcile / mpesa_verify_receipt commands skip needs_review rows
   or are read-only.
 So a needs_review canonical Payment blocked the quote permanently, because
 create_payment_for_quote refuses while one exists.

Added:
 - payments/review_resolution.py: resolve_canonical_payment() and
   resolve_mpesa_payment().
     confirm_paid  needs receipt_number + amount. amount must equal the
                   server-stored expected amount unless override_reason is
                   given. The receipt must match the receipt Daraja reported
                   (case-insensitive) and must not already settle another
                   PAID payment. Canonical path = payments.services.
                   mark_payment_paid (creates/unlocks the ManagedJob and
                   notifies); cashier path = the mpesa_payment_confirmed signal
                   (mpesa_payments.receivers settles the ManagedJob).
     mark_failed   Payment -> failed, its needs_review STK requests -> failed.
                   A fresh payment + STK push is then allowed.
   A reason is always required. Only is_superuser may resolve, enforced in
   the service as well as the view. Every resolution writes a Django admin
   LogEntry via api.admin_audit.record_admin_audit with actor, resolved_at,
   reason, previous status, expected/reported/confirmed amounts, receipt and
   override reason, plus a WARNING log line.
 - payments/services.mark_payment_paid: new keyword amount_override_reason.
   Only the audited resolver passes it; every automated caller keeps the
   strict received == expected check.
 - api/admin_ops_views.py + api/urls.py (same style and permissions as the
   other admin_ops endpoints: IsAuthenticated + IsSuperUser):
     GET  /api/admin/payments/needs-review/
     POST /api/admin/payments/<id>/resolve-review/
     POST /api/admin/mpesa-payments/<id>/resolve-review/
   Body: resolution=confirm_paid|mark_failed, reason, receipt_number, amount,
         override_reason.
 - Choice: an API endpoint rather than a Django-admin action. An action would
   need a custom intermediate form to collect receipt/amount/reason, and the
   admin_ops endpoints are what the ops dashboard already uses.
   "super_admin/platform admin" = is_superuser (same as ADMIN_PERMISSIONS).
   is_staff alone is refused (tested).

Tests: payments/tests/test_needs_review_resolution.py (9). Run against the
pre-step-0 tree they fail 9/9 (8 FAIL + 3 ERROR, counting subtests); all pass
after.
  - non-admin (client, manager, is_staff) -> 403 on list + resolve, no change
  - admin list

#4 Google OAuth (POST /api/auth/social/google/) + scoped throttles
------------------------------------------------------------------------------
- New dependency: google-auth==2.63.1, plus pyasn1 and pyasn1_modules, added
  to requirements.txt. The token is verified with
  google.oauth2.id_token.verify_oauth2_token, which checks signature (Google
  certs), expiry, issuer (accounts.google.com) and aud == GOOGLE_CLIENT_ID.
  The tokeninfo HTTP call and the `requests` import are removed.
- config/settings.py: GOOGLE_CLIENT_IDS is read from GOOGLE_CLIENT_ID
  (comma-separated for web, Android, etc.).
  * Unset: 503 {"code": "google_oauth_not_configured"}. This fails closed,
    and no account is created or looked up.
  * Explicit dev/test override: GOOGLE_OAUTH_DEV_SKIP_AUDIENCE=true skips ONLY
    the audience check. It is honoured only when DEBUG=true and APP_ENV is
    local/dev/test; signature, issuer, expiry and email_verified are still
    enforced (tested).
- email_verified must be true (bool true or the string "true").
- Lookup: by SocialAccount (provider=google, uid=sub) first, then
  User.email__iexact. If two or more accounts match case-insensitively, the
  response is 409 duplicate_email_accounts and nothing is merged.
  EmailAddress is also matched with iexact, so no case-variant duplicate rows
  are created.
- Inactive account: 403 account_inactive, and no tokens are issued.
- Role: chosen ONLY when a new account is created, and only from the
  allowlist. Anything else falls back to client, and partner starts
  unverified. Existing accounts never have assign_role or the partner flag
  touched (the old code called assign_role on every login, which could
  demote a super_admin's stored role). New accounts get an unusable password.
- Duplicate report: `python manage.py report_duplicate_emails
  [--fail-if-any] [--unmasked]` (new, read-only). The equivalent SQL is in
  the command docstring. The existing `normalize_user_emails` dry run also
  lists collision groups.
- Throttles: accounts/throttling.py AuthScopedRateThrottle.
  * It is a ScopedRateThrottle keyed by the real client IP: X-Forwarded-For
    is trusted only from MPESA_TRUSTED_PROXIES, reusing
    payments.callback_security.resolve_client_ip. DRF's stock get_ident uses
    raw XFF when NUM_PROXIES is unset, which would let a client pick a fresh
    bucket on every request.
  * Rates are read from settings at request time.
  * Scopes and defaults, each overridable with THROTTLE_RATE_<SCOPE>:

      Scope                        Default    Endpoints
      auth_login                   10/min     login/, token/
      auth_register                10/hour    register/, register/client|partner|production/
      auth_password_reset          5/hour     password-reset/
      auth_password_reset_confirm  10/hour    password-reset/confirm/
      auth_email_resend            5/hour     resend-confirmation/, email/resend/
      auth_google_login            20/min     social/google/
      auth_invite_claim            10/hour    client-invites/claim/

  * OTP send/verify: the only OTP endpoints are the client-link ones
    (/api/client-portal/links/<token>/otp/request|verify/). They were already
    throttled (client_otp_request 5/hour, client_otp_verify 20/hour) but keyed
    on the raw X-Forwarded-For. clients/throttling.py now uses the same
    trusted-IP key.
  * config/test_settings.py raises ONLY the auth_* rates. The test run shares
    one locmem cache, so production rates would make unrelated tests return
    429. The throttle tests override the rates back down to prove that each
    endpoint returns 429 after its limit.

The bug
  Every tier pays the shop production x shop_floor_multiple (A 1.00, B 1.05,
  C 1.08). It pays the manager min(markup, markup x commission cap), and
  Printy keeps the residual. A markup smaller than the shop uplift divided
  by (1 - cap) made the residual negative. Known case: production 20,000,
  markup 1,000 gives shop 21,600, manager 350, printy_fee -950, against a
  client_total of 21,000. MIN_MARKUP_MULTIPLE (1.05) was imported in one
  place, the partner guardrail, and never enforced in the split.
  Fail-before (code stashed, new tests kept): 16 of the new tests failed
  (9 FAIL, 7 ERROR). After the fix: 23 OK.

Choice: REJECT, not clamp
  A markup below the floor raises MarginFloorError, a subclass of both
  django ValidationError and ValueError. The message gives the minimum
  markup and minimum client price.
  Why:
   - CANONICAL_MODELS.md makes PlatformFeePolicy own the markup caps, and
     the existing upper cap already rejects ("Manager markup exceeds the
     policy cap.").
   - Clamping would silently raise a price the manager typed and may
     already have shown to a client. The stored split would then disagree
     with what was quoted.
   - Subclassing ValueError means callers that already map ValueError to
     400 (partner preview / respond) report it without changes.
     api/exception_handlers.py does not convert a Django ValidationError,
     so views that only caught DRF errors would have returned 500. Those
     views now catch it (see below).

Floor definition (minimum_manager_markup, new, public)
  The larger of these two, in whole KES rounded up:
   1. production x (min_markup_multiple - 1)
   2. the margin floor, so the Printy fee is never negative:
      - fee charged: production x (shop_floor - 1) / (1 - commission cap)
      - fee waived:  production x (shop_floor - 1)
  It then steps up by KES 1 if whole-KES rounding leaves the residual short.
  Effective minimums with the default policy:
    tier A (<1,000):      5.00%, fee waived 5%
    tier B (<=10,000):    9.09%, fee waived 5%
    tier C (>10,000):    12.31%, fee waived 8%
  Invariants are tested over a grid of production 100..500,000, markups
  0..300%, tiers A/B/C, fee charged and waived. They also cover the
  broker_client_price entry point, the direct-shop path
  (production_matching), the public estimate path (calculator_preview) and
  partner preview. Every accepted split has client_total >= shop + manager,
  printy_fee >= 0, and shop + manager + printy == client_total.

New: common/uploads.py, the one validated upload service.
  validate_upload(file, policy) checks, in order:
    1. extension, with Django's FileExtensionValidator against the policy's
       allowlist;
    2. size: empty files and files over the cap are refused;
    3. magic bytes: the first bytes must match the extension, so a renamed

api/payment_views.py - PaymentInitiateSTKView
  quote_id path: the artwork block (_request_artwork_block) is now checked

quotes/acceptance.py - accept_quote_for_payment
  Refuses while quote_request.date_updated is set ("The due date for this
  quote was updated. Please review and acknowledge ..."), next to the
  existing price_updated check. The client-link acknowledgement (commit A)
  and the existing buyer acknowledgement clear it.

quotes/messaging.py - create_quote_message / outbox
  The bug: _send_email_for_message schedules the outbox send with
  transaction.on_commit. In autocommit mode (no surrounding atomic block)
  on_commit runs immediately, so the email was sent and the message updated
  to SENT (or FAILED), and then create_quote_message saved
  email_status=NOT_SENT / email_sent=False over it.
  Fix: NOT_SENT is saved BEFORE scheduling; afterwards the message is
  refreshed so the returned object shows the real outcome. The on_commit
  callback is wrapped (_create_email_outbox_entry_safely) so an outbox
  failure after commit is logged and recorded as FAILED on the message
  instead of raising into the caller's commit. Both contexts are tested:
  autocommit (send happens and stays SENT/FAILED) and atomic (nothing is
  created or sent until commit, then SENT; a rollback sends nothing).

payments/services.py - initiate_stk_push
  - The in-flight check and the new MpesaSTKRequest row are now done in one
    transaction under Payment.objects.select_for_update(), so two
    concurrent requests cannot both see "no prompt in flight" and push
    twice. The Daraja HTTP call runs after the lock is released; the
    PENDING row is what blocks a concurrent second push meanwhile.
  - Stale prompts: PENDING/SENT prompts older than
    MPESA_STK_IN_FLIGHT_SECONDS (default 180s; the handset prompt times out
    after ~1 minute) are marked EXPIRED before the check
    (expire_stale_stk_requests). So an in-flight prompt still blocks a
    conflicting one, but only while it is genuinely in flight - the
    Prompt 1 rule. Before, a prompt whose callback never arrived blocked
    the payment forever (every retry got the dead prompt back).
  - handle_stk_callback: EXPIRED is our own bookkeeping, so a late callback
    for an expired prompt is not dropped as a duplicate. A late success is
    applied with all the usual checks (receipt, exact amount, payment not
    already paid / under review -> needs_review). A late failure is recorded
    on the prompt but never touches the payment.
  - The caller's Payment instance is refreshed (status, Daraja ids) at the
    end, so views that read payment.status after the call keep working.
  - Daraja OAuth token: cached in Django's cache, per base URL + consumer
    key (hashed), for expires_in - 60s (expires_in defaults to 3599). Before,
    every STK push fetched a new token.
  - generate_password used datetime.now() (the OS clock). It now uses
    daraja_timestamp(): timezone.localtime(timezone.now()), i.e. Kenyan time
    from TIME_ZONE=Africa/Nairobi, as Daraja expects.
mpesa_payments/services.py - _timestamp
  Formatted timezone.now() (UTC) directly, so Daraja got a timestamp 3
  hours behind EAT. Now timezone.localtime(...). (Its token was already
  cached in MpesaAccessToken.) This path creates a new MpesaPayment per
  push, so the in-flight/lock rework above does not apply to it.

notifications/services.py - notify()
  notify() has no @transaction.atomic of its own, but it is called from
  atomic services (payments.services.mark_payment_paid via
  _notify_payment_confirmed, jobs/services/managed_job_creation.py,
  mpesa_payments/receivers.py). send_mail ran inside those transactions:
  SMTP held row locks and people were emailed about changes that could
  still roll back. The email now goes through
  transaction.on_commit(..., robust=True): after commit, or immediately
  when there is no transaction; never when the transaction rolls back. A
  send failure is logged at WARNING and never raised (before:
  fail_silently=True, silently dropped).

PROMPT 5 / COMMIT D - audit(#4b): pre-registration account takeover
================================================================================

Investigation - how email confirmation works today
  - ACCOUNT_EMAIL_VERIFICATION defaults to "mandatory" (env-overridable).
    Registration (/api/auth/register/, /client/, /partner/, /production/)
    creates the user with the password the registrant chose plus a primary
    allauth EmailAddress with verified=False, and emails a confirmation link
    to FRONTEND_URL/auth/confirm-email?key=... (ACCOUNT_CONFIRM_EMAIL_ON_GET
    is False; the SPA POSTs the key to ConfirmEmailView, which only verifies
    the address and does not log anyone in).
  - Email/password login and phone login (CustomTokenObtainPairSerializer)
    are refused with EMAIL_UNVERIFIED while the primary address is
    unverified. An unverified phone only resolves an account whose email is
    verified. So the registrant of a squatted address cannot log in yet.
  - Registration of an address already used (any case) is refused.
  - Password reset emails the address only. A reset does NOT confirm the
    address (allauth 65 finalize_password_reset does not), so after a reset
    login still waits for the confirmation link.
  - Phone-first accounts (manager invites, and PATCH /api/auth/me/ for an
    account without an email) attach an address as verified=False.

The takeover (before this commit)
  GoogleSocialLoginView matched an existing account by email (iexact), then
  marked the address verified and linked the Google account, without
  touching credentials. A registrant who squatted victim@x (or a phone-first
  account that attached victim@x) therefore got a working password login -
  and kept any refresh tokens - as soon as the real owner signed in with
  Google once.

Fix (accounts/services/account_security.py, accounts/views.py)
  - email_is_unconfirmed(user, email): the account has EmailAddress rows but
    none verifying this email.
  - On a Google login that matches an existing account by email (not an
    already-linked Google account), under select_for_update on the user, if
    the address is unconfirmed: secure_unconfirmed_account() -
      * set_unusable_password() (this also changes the session auth hash,
        so Django sessions made with the old password stop authenticating);
      * every outstanding simplejwt refresh token is blacklisted;
      * a WARNING is logged;
    and only then is the address marked verified and Google linked. The
    same account is kept; nothing is merged into or from another account,
    and duplicates still get 409. The owner can set a password with the
    normal reset flow.
  - Verified accounts are not touched (password and tokens kept).
Reverse direction
  - Password login: refused before confirmation (checked, no change).
  - Password reset: cannot take over (the link goes to the address) and
    already replaces the registrant's password. Small fix: refresh tokens
    issued before a reset are now blacklisted (they survived a reset).
  - PATCH /api/auth/me/ adding an email (accounts/serializers.py
    UserSerializer.validate_email): an address used by another account in
    any case is refused with 400. Before, a case variant created a
    case-duplicate (which then blocks the real owner's Google sign-in with a
    409) and an exact duplicate was an IntegrityError 500.

Tests: accounts/test_audit_preregistration_takeover.py (16 tests)
  Today's behaviour (controls): registration gives an unverified primary
  address and a link to the address; password login and phone login are
  refused before confirmation; re-registration in another case is refused.
  Google on an unconfirmed account: same account, password unusable,
  address verified, registrant's password login fails; refresh tokens
  issued before are refused (401); the owner's new tokens work; a Django
  session made before stops authenticating; a phone-first account that

  Password reset: link only to the address (control); the reset replaces

  Attach email: a case variant is a 400; an exact duplicate is a 400 not a

  Fail-before (accounts/views.py and accounts/serializers.py stashed, the

Findings (not changed here)
  - Accounts with NO EmailAddress rows (createsuperuser, admin-created,
    pre-allauth) are trusted by password login and therefore by this fix
    too. Recommend a backfill that creates their rows (verified only where
    proven) so the mandatory rule applies to them.
  - Access tokens are stateless: one issued before the Google remediation
    stays valid until it expires (ACCESS_TOKEN_LIFETIME = 30 min). An
    unconfirmed account cannot normally obtain one (login is refused), but
    a per-user token version would close this fully.
  - The secured account keeps what the registrant entered: name, an
    unverified phone, and the role picked at sign-up (e.g. a partner
    applicant). The owner can edit name/phone; a role picked by the
    registrant is not reverted. Not changed, to avoid rewriting account
    data automatically.
  - Password change (PasswordChangeView) does not revoke other refresh
    tokens. Doing so would also log out the current session's refresh
    token; needs a UI decision.
  - A confirmation link sent for a squatted registration still confirms
    that account if the owner clicks it (the owner then has an account with
    the registrant's password). Inherent to link confirmation; the
    confirmation email should say "if you did not sign up, ignore this".
    Copy change for the frontend/email templates.
  - Already-linked Google accounts (matched by Google sub) are not
    re-checked; they were proved when linked.
  - ACCOUNT_EMAIL_VERIFICATION=optional or none would let unconfirmed
    accounts log in; production must keep "mandatory".

Choices and why
- Who generates the code: the PRINTER types it (user wording "the printer
  adds a handover code"). The server only validates/normalises it. A
  system-generated code would need a way to get it onto the parcel, which
  the frontend does not have today.
- Stored plain (not hashed): a 4-12 char code is brute-forceable offline
  anyway; the real protections are (1) never serialized, (2) excluded from
  Django admin, (3) 5-attempt lock, (4) constant-time compare.
- Ops override policy: ops/staff confirming completion ALSO need the code
  (no silent bypass). A buyer who lost the code / locked it goes through
  super-admin dispute resolution, which is logged with a reason and recorded
  as completion_method=admin_dispute. Manager (partner) and printer can never
  confirm (403, unchanged).
- Who may mark dispatched: unchanged (ops/shop/partner); whoever dispatches
  adds the code.

What was built
- jobs.ManagedJobPayout extended (decision 1, no second model; migration
  0009): status needs_review; waiting_reason/detail; audit_log (every
  transition: at, event, source, actor, reason, key, amount); attempt_count,
  next_attempt_at, sent_at; idempotency_key (unique); b2c_conversation_id,
  b2c_transaction_id; reviewed_at/by; index job_payout_due_idx. The unique
  (managed_job, recipient_role) constraint still means one row per party.
- jobs/payout_state.py: ONE state machine used by the manual release, the
  failure recorder, the runner, callbacks and admin review.
    processing -> released only via a B2C callback; -> failed / needs_review
      only via auto/B2C/system
    needs_review -> pending only via admin review; -> released only via a B2C
      callback (late success); -> cancelled
    released, cancelled: final
  Manual release refuses processing / needs_review / cancelled
  (PayoutTransitionError, a ValidationError -> 400 in every release view and
  the Django admin action).
- payments/b2c.py: B2CClient.send() -> /mpesa/b2c/v3/paymentrequest.
  B2CNotSent (OAuth fail, connect timeout, 4xx, ResponseCode != 0) = safe to
  retry with a NEW key. B2CAmbiguous (read timeout, dropped connection, 5xx,
  unparseable body) = never retried automatically. Stub mode never touches the
  network and can never produce a released payout.
- jobs/auto_payouts.py: runner, callbacks, admin actions, money summary.
  Eligibility (re-checked under row locks, job then payout, at send time):
  completed with buyer_handover/admin_dispute; no open dispute; no lateness
  hold (payout_hold); payment verified (a Payment paid, none needs_review).
  A held rush premium does NOT block (decision 2), and the money summary
  shows it. Amounts come from the stored QuoteFinancialSplit and must match
  the job/assignment copies, be whole KES, and shop+manager <= client_total.
  Payee: can_receive_payouts + verified phone, otherwise pending with a
  waiting_reason. Limits: AUTO_PAYOUT_MAX_AMOUNT per payout,
  AUTO_PAYOUT_DAILY_CAP per Nairobi day -> needs_review.
  Send: commit `processing` + key PRINTY-PO<id>-A<n> BEFORE the request.
  Retry with backoff base*2^(n-1); after AUTO_PAYOUT_MAX_ATTEMPTS ->
  needs_review retries_exhausted. No result in
  AUTO_PAYOUT_RESULT_TIMEOUT_MINUTES -> needs_review.
  Callbacks: matched on key + stored ConversationID. Success needs a receipt +
  the exact amount. Duplicate = no-op; unknown/stale/mismatch/wrong amount
  change nothing. A queue timeout -> needs_review. When all payouts for a job
  are released, job.payment_status=released and the event
  payout_released_auto is recorded.
- Decision 4: AUTO_PAYOUTS_ENABLED on -> dispute "release" only clears the
  hold and completes the job; the runner pays. Off -> unchanged manual
  release. A release blocked by an in-flight/review payout now returns 400
  release_blocked and rolls the resolution back (it was a 500 before).
